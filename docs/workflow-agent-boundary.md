# 当前工作流与 Agent 内核的边界

日期：2026-10-09。基于当前 `server/agent.ts`、`server/runner.ts`、`server/sources.ts` 与实际阅读工作流；本文讨论 MVP 之后的方向，不代表已实现这些扩展。

当前 MVP 可以用直接 LLM API 完成。产品的价值是方便交付来源、可靠后台执行、取得结果与继续追问；自主 Agent 不是这些体验成立的前提。

## 现在实际使用了什么

程序负责文章正文获取、字幕优先、无字幕转写、完整性校验、缓存、任务队列、错误状态与结果保存。模型收到已经获取的全文，只负责总结和基于来源继续回答。

Pi 的 `createAgentSession` 显式设置 `tools: []`、`customTools: []`；自动 skills、扩展、上下文文件发现也关闭。两个 `SKILL.md` 由程序按来源类型选取并放入系统提示，因此目前是总结规则，不是模型自主发现、选择和执行工作流。

Pi 现在提供持久聊天会话、历史上下文、自动压缩、流式事件、调用重试和取消。业务任务的回执、恢复、串行/并发与来源缓存仍由应用处理。这些基础设施节省了实现工作，但不能据此说当前产品已经具备自主规划、工具选择或编码能力。

直接接入 LLM API 也能完成相同功能；需要继续实现或复用历史存储、上下文裁剪/压缩、流式处理、重试和取消。SDK 通常只解决其中一部分。因此“只接 LLM”指模型执行层可以更简单，不是删除现有任务和采集后端。

## 什么需求才值得引入自主工具循环

| 用户目标 | 推荐形态 | 原因 |
|---|---|---|
| 总结文章/视频、解释其中一段、按固定格式重写 | 程序工作流 + LLM | 已知输入、步骤和结束条件 |
| 比较用户给定的三篇文章、每天生成摘要 | 多来源工作流 / 调度器 + LLM | 多步骤、定时运行本身不要求自主规划 |
| 核验文章观点，找原论文与官方资料，发现矛盾继续查证 | 限定工具的阅读 Agent | 查什么、是否追加检索、如何补足证据依赖中间结果 |
| 联系过去收藏的资料，形成专题研究并更新笔记 | 检索工作流起步，出现开放研究需求后使用 Agent | 简单检索可以用 RAG；自主找缺口、跨资料研究与更新需要进一步编排 |
| 把视频教程做成可运行 demo，运行测试并修复 | Coding Agent + 独立工作区 | 文件读写、命令执行、运行反馈与迭代修复正是 coding harness 的用途 |

工作流与 Agent 的实用区别是：下一步由固定程序决定，还是由模型根据工具返回动态决定。Agent 仍然是 LLM 加工具和执行循环；接入一个内核不会凭空增加领域知识、采集成功率或记忆质量。这个区分与“从最简单有效方案开始”的原则参见 [Anthropic 官方工程文章](https://www.anthropic.com/engineering/building-effective-agents)。Pi 的会话、压缩、工具与事件接口见 [官方 SDK 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)。

## 建议的推进方式

1. **MVP 先保持当前适配器。** 完成来源成功率、时长、摘要质量、后台与追问体验验收。Pi 已运行，没必要只为了名称更准确立刻重写。也不为了使用内核而把确定的抓取和转写交给模型。
2. **先验证“阅读后查证”。** 复用现有来源获取函数，按需增加 `search_web`、`read_source`、`find_saved_sources` 等明确的业务工具，让模型在可限定次数与预算的范围内选择下一步。以查证结果是否更有用来决定是否继续，而不是以工具调用数量验收。
3. **有真实编码任务再开放 coding 能力。** 独立工作区内生成文件、运行命令、检查产物；手机仍是任务与结果入口。不要默认把阅读后端变成拥有整台电脑权限的终端助手。

`AgentBackend.run()` 已把任务服务与模型运行层分开，后续可以实现直接 API 的适配器，或在 Pi 中注册阅读工具。现有会话使用 Pi session 文件，替换内核仍需要迁移/重建上下文，不能当作无需处理历史的一键切换。业务保存的来源、消息与结果应继续作为可恢复的数据，不只依赖内核压缩后的上下文。

“自用 Personal Agent 的方便入口”可以继续作为产品定位；技术上当前版本准确地说是 **阅读工作流 + 会话式 LLM**。没有必要为了符合 Agent 标签而增加自主执行。
